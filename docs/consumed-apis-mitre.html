Two device sources — PennDOT TSAMS and MaineDOT — are static GIS asset inventories with no message field and no timestamp. what varies per request

Five values in the tables above are filled in at call time rather than fixed. This is what each one is, the code that derives it, and what it costs in requests.

{minLon},{minLat},{maxLon},{maxLat}TomTom Traffic Incident Details v5A bounding-box tile. TomTom caps one bbox at 10,000 km², so a corridor cannot be queried in a single call — it is covered by a chain of tiles.services/tomtom-incidents.js has two tilers. corridorTiles() walks the corridor polyline accumulating points and, as soon as the next point would push the bounding box past maxAreaKm2, emits the box built so far and starts a new one at that point. pointsToTiles() instead buckets the active work-zone coordinates onto a coarse grid and emits one padded tile per OCCUPIED cell, so N clustered zones cost far fewer requests than one bbox per zone. Both pad in kilometres converted to degrees: dLat = padKm / 110.574 and dLon = padKm / (111.320 × cos(midLat)).corridorTiles: maxAreaKm2 9500 (under TomTom's 10,000), padKm 10, maxTiles 90. pointsToTiles: cellDeg 0.8 (≈7,100 km² even at Florida's latitude), padKm 3, maxTiles 220.One request per tile per poll. Corridor tiles are deduped on a ~0.25° grid so overlapping directions and corridors do not pay twice. Self-capped by DAILY_BUDGET (default 2500/day, TOMTOM_DAILY_BUDGET to override); corridor TTL 45 min, zone TTL 6 h.
{lon1},{lat1};{lon2},{lat2}OSRM route service v1The work zone's own two endpoints — the start and end coordinate of the event being snapped to the road network.backend_proxy_server.js snapToRoad(lat1, lng1, lat2, lng2, direction, corridor, state, eventId, stateKey) receives the event's primary and secondary points straight from the feed record and passes them through to snapToRoadImmediate(), which builds the URL. Note the order flips: OSRM takes lon,lat while the feeds carry lat,lng.overview=full & geometries=geojson on every call. 10 s timeout (12 s for the via variant).Effectively one request per distinct zone geometry, ever. getOSRMCacheKey() rounds both endpoints to 5 decimal places (~1 m) and appends a normalized direction; the result is persisted in the osrm_geometry_cache table, so a repeat of the same zone is served from the database and never re-requested.
